# 백업 재생 검증

과거 백업 DB의 글을 감시기 파이프라인에 다시 흘려 보내 적정가 보강이 실제 글에서 오류 없이 돌아가는지, 얼마나 빠르고 메모리를 얼마나 쓰는지, 알림이 얼마나 나가는지 확인했다. 이 문서에는 집계 값만 있다. 글 제목, 작성자, 연락처, 글번호는 싣지 않았다.

- 검증일: 2026-10-20(처음 검증은 2026-10-18 번들로 했고, 현재 번들로 같은 구간을 다시 돌렸다)
- 대상 코드: 브랜치 `feature/fair-price-alerts` 작업 사본(커밋 전)
- 적정가 번들: `fairprice-1.0@2026-10-19T12:32:24+00:00`(학습 행 3,141, 판매자 단위 5겹 CV MdAPE 22.3%, P10~P90 포함률 80.1%)
- 도구: `tools/replay_backup.py`
- 2026-10-18 번들(`fairprice-1.0@2026-10-18T07:56:48+00:00`)과 비교: 같은 800건에서 묶음 제외 54 → 57건(묶음 판정 개정), 적정가 산출 86.5% → 86.1%, `[저평가]` 8 → 12건, `deals` 알림 63 → 64건. 오류는 두 번들 모두 0건이다.
- 배포 전 스테이징 점검(운영 DB 사본, 새 이미지 컨테이너 안): 테스트 383 passed · 1 skipped, 마지막 800건 재생 오류 0건, 연락처 유출 0건, 적정가 산출 87.9%.

## 방법

### 데이터

- 백업 DB: 분석 컨테이너의 `/scratch/raw/drspark_seen.db`. `seen` 5,584건, 관측 기간 2026-03-05 ~ 2026-10-16. 읽기 전용(`mode=ro`)으로 열었다.
- 재생 구간: 관측 시각 순으로 마지막 800건. 2026-10-04 ~ 2026-10-16(12.1일, 하루 65.9건).
- 사전 적재: 재생 구간 시작 전 180일(재게시 조회 기간) 안의 글 3,227건을 임시 DB의 `seen`에 먼저 넣었다. 운영 DB에 이미 쌓여 있었을 이력이다.
- 비교 기준: 분석 저장소 `data/curated/listings_clean.parquet`의 재게시 묶음(`item_id`, `item_seq`)과 최종 라벨, `fair_price_estimates.csv`의 폴드 밖 적정가.

### 절차

1. `/tmp` 아래 임시 폴더에 새 DB를 만들고 `source.init_db()`로 테이블을 만든다(`seen`, `enrichment`, `alert_outbox`).
2. 운영의 `__main__`과 같이 `Enricher.from_env()`로 `pricing_data/`를 읽어 `source.ENRICHER`에 넣는다. 걸린 시간과 RSS를 잰다.
3. 재생 구간의 글을 시간 순으로 하나씩, `run_once`가 상세 파싱 뒤에 하는 순서 그대로 처리한다.
   `save_item` → `enrich_item` → `should_alert` → `build_payload`
4. `should_alert`는 모듈 설정(`ALERT_MODE`, `ALERT_CATEGORIES`, `ALERT_SKIP_WANTED`)을 바꿔 가며 네 가지 시나리오로 부른다.
5. Discord로는 보내지 않는다. 웹후크는 비워 두고 `requests.post`도 막았다.
6. 끝나면 임시 폴더를 지운다. 백업에 작성자·연락처가 있기 때문이다.

백업 `seen`에는 썸네일, 거래지역, 상태 목록의 네고·거래방법이 없다. 이 값은 비워 두었다. 그래서 임베드 크기는 실제보다 조금 작게 나온다(거래지역 필드는 최대 200자).

### 환경

분석 컨테이너(Python 3.12, pandas 2.2.3, numpy 2.1.3, scikit-learn 1.5.2, lightgbm 4.5.0, Docker Desktop/Windows)에서 측정했다. 운영 서버와 하드웨어가 달라 시간 값은 참고용이다.

## 표본 안 판정 주의

적정가 모델(`fairprice-1.0`)은 백업의 2026-03 ~ 2026-10-16 글로 학습했다. 재생한 800건 중 565건(70.6%), 최근 200건 중 160건(80%)이 학습 행(`in_price_model`)이다. 학습 행이 아닌 235건 중 119건은 같은 매물의 가장 최근 글이 학습에 들어간 이전 재게시 글이다. 나머지는 대부분 묶음·구매 글·장비 외 품목처럼 적정가를 내지 않는 글이다. 학습한 글은 모델이 그 호가를 이미 봤기 때문에 적정가가 호가 쪽으로 끌려간다. 그래서 위의 저평가·고평가 건수는 실제 운영보다 적다.

표본 밖 효과를 가늠하려고 분석 저장소의 폴드 밖 적정가로 바꿔 계산했다. 판매자 5겹 CV에서 그 판매자를 보지 않은 모델이 낸 P10/P50/P90이다(`fair_price_estimates.csv`, `oof=True`). 적정가가 있는 글 중 이런 값이 있는 559건에만 모델 출력을 바꾸고 `Enricher.enrich`를 다시 불렀다. 판정·신뢰 규칙과 `should_alert`는 그대로 썼다.

| 559건 | 표본 안(배포 모델) | 표본 밖(폴드 밖 모델) |
|---|---:|---:|
| 저평가 | 19(3.4%) | 46(8.2%) |
| 고평가 | 30(5.4%) | 48(8.6%) |
| 가격 확인 필요 | 5 | 14 |
| 적정 범위 | 505 | 451 |
| `[저평가]` 알림(신뢰 높음·보통) | 11 | 24 |

- 두 P50의 차이(|log| 기준)는 중앙값 9.5%, p95 49%다.
- 800건 `deals` 알림은 64건(하루 5.3)에서 74건(하루 6.1)이 된다. 저평가는 25건, 가격 인하는 49건이다. 저평가 알림만 보면 하루 1.0건에서 2.1건 정도로 늘 것으로 본다.
- 폴드 밖 값은 분석의 최종 라벨(LLM 검수 포함)로 만든 것이다. 감시기의 규칙 식별과 다를 수 있어 근사치다.
- 분석의 시간 홀드아웃(2026-08-31까지 학습, 2026-09-01 ~ 10-16 평가, 1,312건) 결과는 MdAPE 22.9%, P10~P90 포함률 80.5%다(`pricing_data/fairprice.json`). 운영에서도 예측구간 밖(저평가·고평가)은 판정이 난 글의 약 20% 안팎으로 예상한다.

## 한계

- **표본 안 판정.** 위 절에서 본 대로 저평가·고평가 건수는 운영보다 적게 나온다.
- **비시즌 구간.** 재생 구간은 10월 초·중순이다. 시즌 중(11~2월)에는 글 수와 `deals` 알림이 더 많을 수 있다.
- **백업에 없는 필드.** 썸네일, 거래지역, 네고·거래방법은 비워 두었다. 페이로드 크기 검사는 그만큼 여유가 있다.
- **재게시 기준.** 사람이 검수한 정답이 아니라 같은 규칙으로 만든 분석 묶음과 비교했다. 닉네임을 바꾼 재게시나 제목·스펙을 크게 바꾼 재게시는 둘 다 놓친다.
- **측정 환경.** Docker Desktop(Windows)에서 쟀다. 운영 서버의 CPU·디스크에서는 시간 값이 다를 수 있다. 메모리는 비슷할 것으로 보지만, 컨테이너 메모리 제한이 512MB 이상인지 확인하는 것이 좋다.

## 다시 돌리기

분석 컨테이너 안에서 돌린다. 원본 백업은 읽기만 하고, 임시 DB는 `/tmp` 아래에 만들었다가 지운다. 출력은 집계 값뿐이다. 아래 명령은 분석 저장소 루트(`analysis/drspark`, `bin/dx`가 있는 폴더)에서 실행한다.

```bash
cd <분석 저장소 루트>

# 마지막 800건(기본), 집계 JSON은 컨테이너의 /tmp에
bin/dx sh -c 'cd /work/alarm && python tools/replay_backup.py -n 800 --json /tmp/replay_800.json'

# 최근 200건
bin/dx sh -c 'cd /work/alarm && python tools/replay_backup.py -n 200 --json /tmp/replay_200.json'

# 이력 없이(재게시 탐지가 구간 안에서만), 보강을 끈 채로(기존 동작 확인)
bin/dx sh -c 'cd /work/alarm && python tools/replay_backup.py -n 800 --no-history'
bin/dx sh -c 'cd /work/alarm && python tools/replay_backup.py -n 800 --no-pricing'
```

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--db` | `/scratch/raw/drspark_seen.db` | 원본 백업(읽기 전용) |
| `-n` | 800 | 재생할 마지막 글 수 |
| `--no-history` | (사전 적재함) | 구간 앞 180일의 글을 임시 DB에 넣지 않는다 |
| `--lookback-days` | 180 | 사전 적재 기간 |
| `--listings` | `/work/data/curated/listings_clean.parquet` | 재게시·라벨 비교 기준(없으면 건너뜀) |
| `--oof` | `/work/data/curated/fair_price_estimates.csv` | 폴드 밖 적정가(없으면 건너뜀) |
| `--pricing-dir` | 저장소의 `pricing_data/` | 적정가 번들 폴더 |
| `--no-pricing` | | `DRSPARK_PRICING=0`으로 돌린다 |
| `--tmp` | `/tmp` | 임시 DB를 만들 폴더 |
| `--keep` | | 임시 폴더를 남긴다. 연락처가 든 DB가 남으므로 확인 후 지운다 |
| `--json` | | 집계 결과 JSON 경로(저장소 밖 권장) |

분석 저장소 없이 운영 DB 사본만으로 돌릴 때는 `--listings "" --oof ""`로 비교 기준을 끈다([docs/DEPLOY.md](DEPLOY.md)의 시작 전 점검). 어느 단계에서든 오류가 있으면 종료 코드 1을 돌려준다. 800건은 1분 정도 걸린다.
